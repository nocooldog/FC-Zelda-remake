# 塞尔达一代重制：项目定义与 Raft 协作方案

版本：V0.1  
日期：2026-09-10  
用途：项目留存、同步开发 Agent、启动资源盘点与可玩样板。  
状态：启动草案。明确区分用户目标、推荐默认方案和待确认事项；不代表完整开发排期已获确认。

## 1. 项目目标

将 NES《塞尔达传说》一代重新制作成具有 GBA《塞尔达传说：缩小帽》式二维像素美术与表现的游戏。

核心目标：保留一代的探索辨识度，用更丰富且一致的环境、人物、动画和界面呈现，并通过实际试玩决定必要的操作改善。

当前最重要的验证：现成项目能减少多少工作；能否实现目标美术与手感；开发 Agent 能否稳定完成修改、运行、验证和交付。

## 3. 范围与边界

### 3.1 推荐保留

- 世界与房间之间的连接关系。
- 迷宫的主要结构、关键道具、秘密及探索路线。
- 原版的核心探索节奏与辨识度。

保留结构不要求逐像素复制：人物和地形视觉尺寸改变后，可调整局部间距，但须检查道路可达性、碰撞和战斗平衡。

### 3.2 推荐升级

- 人物、敌人、地形、洞穴和界面的像素美术。
- 行走、攻击、受击、死亡及环境动画。
- 必要的输入、交互和存档体验。

### 3.3 当前不纳入

- 缩小机制、新剧情、新迷宫、多人与联网功能。
- 第二轮冒险、移动端适配、GBA 原生移植。
- 自研通用游戏引擎、大型插件体系或多 Agent 自动游戏生产平台。

移动方向、刺剑或挥剑、攻击距离、无敌时间等，属于样板中的明确设计参数。不得直接引入全部《缩小帽》动作而不检查原版敌人平衡。

## 4. 首个可玩样板

目标体验长度约 5—10 分钟；这不是交付工期承诺。

### 4.1 内容

1. 林克出现在开局场景。
2. 进入洞穴，与老人交互并获得剑。
3. 出洞，与一种代表性敌人战斗。
4. 切换至相邻场景，再返回。
5. 保存、退出并读取，正确保留取剑状态。
6. 验证受击、死亡与重新开始的基本路径。

地图只制作满足上述流程所需的开局室外、取剑洞穴和相邻室外场景。第一座完整迷宫属于样板通过后的下一里程碑。

### 4.2 两步交付

- 功能样板：使用简单占位素材跑通流程，明确碰撞、动作与状态。
- 风格样板：在同一流程上替换目标美术、动画和界面，保持功能可用。

不要先生产全地图美术，也不要同时制作两个引擎版本。

### 4.3 验收

| 维度 | 标准 | 证据与责任 |
| --- | --- | --- |
| 运行 | 在约定电脑环境按说明可以启动 | general 提供版本、步骤和运行记录 |
| 游戏流程 | 取剑、战斗、切图、死亡重试能够完成 | general 自检，用户试玩 |
| 状态 | 读档后取剑状态正确；场景往返无重复奖励异常 | general 提供检查记录 |
| 画面 | 比例、色彩、地块拼接、遮挡和动画一致，无明显破损 | 截图或录像；用户判断风格 |
| 操作 | 移动、攻击和受击可理解、无明显卡住或穿墙 | 用户实际试玩 |
| 可维护性 | 能依据反馈修改并复查已有流程 | general 提交变更与回归结果 |

无报错不等于验收通过；无窗口检查不代替画面检查和实际手感测试。

## 5. 资源盘点

只盘点样板需要的资源。scout 对每项给出来源、版本或提交号、授权说明、实际核查程度、缺口和建议。

| 类别 | 首轮盘点内容 |
| --- | --- |
| 引擎与代码 | 是否能运行；所需依赖；Agent 可否修改和验证；四项核心功能缺口 |
| 人物 | 站立、行走、攻击、受击和死亡动画；方向与尺寸一致性 |
| 环境 | 草地、树木、岩壁、洞口、洞穴内部；拼接与遮挡规范 |
| 敌人 | 一种敌人的移动、攻击、受击与死亡 |
| 界面与音效 | 对话、生命值、保存提示及必要反馈 |
| 原版资料 | 场景出口、障碍、事件、敌人位置与取剑条件 |
| 使用条件 | 区分代码许可证、美术音频使用条件，以及只用于参考的材料 |

建议清单字段：资源名称｜用途｜来源链接｜版本/提交号｜许可证或使用条件｜核查状态｜缺口｜负责成员。

核查状态使用：已找到、已阅读、已运行、已验证。不能把仓库 README 中的描述写成团队已经测试通过。

## 7. Raft 小组协作

本方案按用户提供的职责设计，不假设 Raft 已支持共享文件、自动转派、消息触发或成员共用终端。Cindy 首先核实能力。文档中的 @ 名称是任务归属标记，不表示已经发送任务。

| 成员 | 项目职责 | 主要交付 | 职责边界 |
| --- | --- | --- | --- |
| @Cindy | 协调任务、维护优先级、检查交付、汇总用户待决策项 | 当前里程碑、任务状态、验收结论 | 不替用户判断手感；不把成员自报完成直接当验收通过 |
| @general | 主开发与集成；运行项目；实现功能；整理运行证据 | 源码、可运行版本、检查记录 | 作为唯一主集成负责人；重大范围或引擎变更先交 Cindy 收口 |
| @scout | 调研仓库、资料、素材与许可；核实原版机制 | 资源清单、缺口、明确技术建议 | 区分事实和推断；未经安排不修改主开发代码 |
| @writer | 维护定义、决策记录、任务说明、使用说明和阶段总结 | 一致且可追溯的项目文档 | 不擅自新增需求或把建议改成已确认结论 |
| 用户 | 决定产品取舍、视觉偏好、玩法方向；试玩验收 | 关键决策与优先反馈 | 不承担持续盯人和逐条转述成员消息 |

### 7.1 协作流程

1. Cindy 发出目标明确、范围有限且有验收条件的任务。
2. scout 先核查影响选型或实现的资料；general 可同时做独立的环境检查；writer 整理已有定义。
3. Cindy 将需要的证据与决策交给 general，开始有依赖关系的实现。
4. general 完成自检并交付可运行版本，writer 更新操作与变更说明。
5. Cindy 检查是否符合任务范围，再提交用户试玩；将反馈整理为下一轮优先任务。

协调、实施、验收按依赖推进。不要让四名成员同时重写项目定义或同时修改核心代码。

### 7.2 共用任务格式

- 任务编号与名称。
- 负责人。
- 目标与输入资料。
- 范围及不包含内容。
- 依赖任务。
- 交付文件或运行版本。
- 验收标准与实际证据。
- 状态：待开始 / 进行中 / 待验收 / 完成 / 受阻。
- 阻碍与需要谁做出的具体决定。

### 7.3 文档与代码协作规则

- 以共同仓库或明确共享目录中的文件为准，不依赖聊天上下文作为唯一记录。
- 使用版本控制；general 负责主代码集成。writer 主要维护文档，scout 主要维护调研记录。
- 未确认有共用目录时，由 Cindy 明确材料传递方式，不假设另一成员已看到文件。
- 每个里程碑保留可运行版本、启动说明和已知问题。
- 常规可逆实现由负责人推进；平台变化、引擎切换、范围增加、付费采购或公开发布需交由用户决定。

## 9. 给 Cindy 的启动说明

请将本文件作为项目启动上下文。你的首要任务是让团队完成样板资源盘点与技术核查，并组织一段可运行样板的开发。

先执行 P00，明确实际开发环境和文件共享方式；随后安排 scout 执行 R01/R02、general 执行可独立进行的 E01、writer 执行 D01。依赖未满足的实现不要提前启动。

采用推荐默认方案推进可逆工作。只把会改变路线、产生明显返工或需要用户实际偏好的问题集中交给用户。每次汇报给出：当前可用成果、证据、主要阻碍、下一步；有明确推荐时同时提供推荐与依据。

不要将本文件理解为全游戏开发、采购或公开发布授权。当前重点是范围明确的样板验证。所有“完成”必须对应文件、可运行版本或可复查证据。
